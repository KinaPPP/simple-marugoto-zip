# v1.3.14 X・20枚投稿の診断版

現行v1.3.13を基に、Xの1投稿20件の画像・動画を取得できるか確かめるための診断を追加しました。投稿単位の重複除外や画像URLの抽出ルールは変えていません。正式な20枚対応を保証する版ではなく、実際のXの応答を調べる版です。

## 更新とテストの手順

1. 収集中なら停止してから、既存の読み込み元フォルダへ上書きし、Chromeの拡張機能画面で再読み込みしてください。設定・進捗の削除や再インストールは不要です。
2. **対象のXタブも再読み込みしてください。** 拡張機能を更新するだけでは、開いているXタブに旧版の監視処理が残る場合があります。
3. 可能なら、まだ収集していない20枚投稿のあるアカウントで、対象投稿が含まれる位置まで手動収集してください。対象投稿のURLも控えてください。既存データを削除して試す必要はありません。
4. 収集完了後、「ダウンロードファイル数」を**無制限**にして保存します。5ファイルのままなら20枚を一度には保存しません。分割ZIPの場合は、対象の20ファイルが複数ZIPに分かれる場合もあります。
5. 保存先の選択は従来どおり別タブです。「常に許可」が未選択・表示されない・不明の場合は連続保存終了まで選択タブを残してください。
6. テスト後、設定→**保存先・X収集の診断ログ**を開いてください。Xの一覧で対象投稿IDの件数・番号を確認し、「診断ログをJSONで保存」を押します。
7. JSONと、対象の20枚投稿URL、実際にZIP内に何枚入っていたかを共有してください。ログの内容は共有前に確認してください。

再現中は設定・診断ログ画面を閉じておいてください。表示タブが保存先の許可へ影響する可能性があります。ログは最新400件なので、問題発生後は長く収集を続けず、なるべくすぐに書き出してください。

## 記録する内容

- 投稿IDと通信の種類（UserMedia、TweetDetailなど。通信URL自体は記録しません）
- Xの応答内のメディア数、最初に同じ投稿を見た時の数、抽出できた画像数・動画数
- 同じ投稿を既に処理したため応答を除外したかどうか
- 収集状態へ記録した実件数、新しく追加した件数
- 現在の収集状態に残るメディア番号と、保存済みキーで確認できる番号
- 既存の抽出対象とは別の mediaDetails / media_details 配列が見つかった場合の件数

主に5件以上のメディアを含む応答を記録します。「最初4件→後から同じ投稿20件」の場合も後の応答に最初の件数を記録するため、除外の理由を調べられます。通常の1〜4件投稿すべてをイベントに記録する方式ではありません。

診断画面は現在データから、5件以上を収集した投稿と、直近のログで確認した投稿をアカウントごとに最大100件表示します。Xから届いた最大件数は直近400件のログから集計するため、古いログが消えた場合は不明になります。保存済みキーがない旧データの保存数を推測して成功扱いにはしません。

Xから4件以下しか届かなかった場合などは、20枚投稿と通常の4枚投稿をこの診断だけでは区別できず、一覧に出ないことがあります。その場合も対象の投稿URLとログが手掛かりになります。未知の返却形式をすべて検出することを保証する機能ではありません。

## プライバシーと保存処理

ログには投稿ID、アカウント名、メディア件数・番号を含みます。保存先診断のフォルダ名・ZIP名等も既存どおり含みます。画像本体、投稿本文、メディアURL、トークン、Cookieは追加診断の記録対象にしていません。既知の秘密情報形式のマスクは維持していますが、完全な匿名化を保証するものではないため、共有前に内容を確認してください。

診断は拡張内の既存のログ領域に保存し、勝手に外部送信しません。通常の収集・ZIP/JSONバックアップには診断ログを混ぜません。「診断ログだけを消去」で収集進捗は削除されません。

画像収集や重複除外の判定は変更していません。診断の失敗で本来の抽出を中断しないようにしています。診断イベントや保存処理が増えるため、タイミングや負荷に影響する可能性はあります。

## 検証

20画像、画像10件＋動画10件、画像URL欠落、4件→20件の同一投稿の再応答、fetchとXHR、受信側の起動前の応答、診断失敗時の収集継続、診断メッセージの送信元と項目制限、収集件数の保存、JSON書き出しをオフラインで検証しています。全27テストファイルと全44 JS/CJSファイルの構文チェックが成功しました。実際のXの20枚投稿での確認はこれからです。今回は別モデルへのレビュー依頼は行っていません。

配布ZIPにはverificationや各試験版のCHANGE-NOTESを入れません。機能に必要なdebugフォルダは含めます。検証ログと過去の変更メモは開発作業領域に残します。
