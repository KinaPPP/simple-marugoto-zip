# シンプルまるごとZIP / simple-marugoto-zip 仕様書

作成日: 2026-09-19  
ステータス: v1.0.0 X向け初回正式版（v0.0.24実機確認済み）

## 1. 目的

対応SNSで現在開いているユーザーアカウントを対象に、そのアカウントが投稿した画像・動画をまとめて収集し、整理済みZIPとして保存するChrome拡張機能。

初期実装はX（旧Twitter）を対象とするが、コア処理とSNS固有処理を分離し、将来的にBluesky・ThreadsなどをProvider追加で対応できる構造にする。

「シンプル」シリーズ共通の思想として、ユーザーに判断させる必要のない設定は極力見せず、少ない操作で目的を達成できることを優先する。

既存の「シンプルイメージコピー」は現在表示中のHTML/DOMから画像を抽出して選択保存する汎用ツールとして維持し、本拡張はSNSアカウント単位の大量アーカイブ用途として新規実装する。

---

## 2. 基本操作

1. 対応SNSで保存したいユーザーのプロフィール・メディア・投稿ページを開く。
2. 拡張機能アイコンを押す。
3. 現在のページから対象ユーザー（例: `@ppp200x`）を自動判定する。
4. 「メディアを収集」を押す。
5. Xでは「自動／手動」の収集方法を選択。自動はXの通信完了を待って画面を遡り、手動はユーザー自身が `/media` をスクロールして発生した通信だけを受動収集する。手動モードではユーザーが「収集を完了」を押す。
6. 収集完了後、取得対象（画像 / 動画）とZIP分割方法を選ぶ。
7. 「ZIPで保存」を押す。
8. 画像・動画を取得し、種類別フォルダへ整理してZIP保存する。

---

## 3. 対象SNS / 対象ユーザー判定

現在開いているURLからSNSと対象ユーザーを自動判定する。SNSを手動で選ばせる設定は原則として設けない。

### 3.1 X（v0.0.1で実装）

想定例:

- `https://x.com/ppp200x`
- `https://x.com/ppp200x/media`
- `https://x.com/ppp200x/status/1234567890`

上記はいずれも `@ppp200x` を対象として扱う。

`/home`、`/search`、`/notifications` など対象ユーザーを一意に決められないページでは収集を開始せず、プロフィール等を開くよう案内する。

### 3.2 将来Provider

- Bluesky
- Threads

Provider追加時も、ポップアップUI・ZIP・レジュームなどの共通処理は変更せず、SNS固有の「ユーザー判定」「投稿列挙」「メディアURL取得」だけを差し替える。

---

## 4. 取得対象

UI上の分類は次の2種類のみ。

- 画像
- 動画

SNS上のアニメーションGIFは実体としてMP4で配信されるため、UI上では「動画」に含める。GIF専用チェック項目は設けない。

### 4.1 画像

- 各SNSで取得可能な最大・原寸相当の画像を優先して保存する。XではCDNの `orig` を優先する。
- JPEG / PNG等、各SNSが配信している形式をそのまま保存する。
- JPGまたはPNGへの強制変換は行わない。
- 「画像品質」「画像形式」の設定項目は設けない。

注意文:

> 画像は常に原寸でダウンロードされます。画像によってはファイルサイズが大きくなる場合があります。

### 4.2 動画

- 通常動画は取得可能な動画バリアントのうち最高品質を優先する。XではMP4の最高ビットレートを優先する。
- SNS上のアニメーションGIFもMP4として保存し、「動画」に含める。

## 5. ファイル名

基本形式:

```text
{Post ID}_{投稿内メディア番号}.{拡張子}
```

例:

```text
2101040138784829824_1.jpg
2101040138784829824_2.jpg
2101189548885831967_1.mp4
```

Providerが返す一意なPost IDを利用するため、投稿間のファイル名衝突を避けやすく、同一投稿内の複数メディアも番号でまとまる。

ユーザー向けのファイル名・ソート順変更オプションは設けない。

---

## 6. ZIP構造

画像と動画の両方を選択しても、種類別に別ZIPを作らず、同一系列のZIPへ保存する。

ZIP内部でフォルダ分けする。

```text
ppp200x_20260921_211100_media_001.zip
└─ ppp200x/
   ├─ images/
   │  ├─ 2100842708860572051_1.jpg
   │  └─ ...
   └─ videos/
      ├─ 2101189548885831967_1.mp4
      └─ ...
```

分割が必要な場合:

```text
ppp200x_20260921_211100_media_001.zip
ppp200x_20260921_211100_media_002.zip
ppp200x_20260921_211100_media_003.zip
```

完成済みZIPは後から開き直して追記しない。

---

## 7. ZIP分割

UI候補:

- 自動（既定）
- 500 MB
- 1 GB
- 500ファイル

「自動」は実装上、安全側の容量上限とファイル数上限のうち先に到達した条件で分割する。

v0.0.24時点の自動分割の設定:

- 最大 300 MB
- または最大 300ファイル

どちらかを先に満たした時点でZIPを確定する。

メディアファイルは既に圧縮済みのJPEG/PNG/MP4が中心のため、ZIPでは再圧縮せず格納（STORE）を基本とする。

## 8. 収集処理とレート制限

大量取得で重要なのは実ファイルのダウンロードより、Xのタイムライン・検索結果を遡る際のアクセス回数。

方針:

- X自身のWeb画面が行う読み込みを利用し、短時間に大量の独自APIリクエストを並列送信しない。
- v0.0.17では `UserMedia` 等の関連通信の開始・終了を監視し、通信完了後にsettle時間を置いてから次のスクロールへ進む。
- v0.0.18以降は設定タブの開発用診断から疑似429を発生させ、実際の429検出と同じ停止・待機・自動再開経路をテストできる（HTTP通信は改変しない）。
- 前回スクロール後に関連通信が起きない場合だけ、低頻度で最下部を再確認する。固定短周期で盲目的にスクロールし続けない。
- 429（Too Many Requests）等のアクセス制限を検知したら処理を停止・待機する。
- 制限を強引に回避する処理は実装しない。
- 同一Tweet / メディアの重複はPost ID + メディア番号で排除する。

### 初期取得戦略

1. 対象ユーザーの `/media` タイムラインを利用する。
2. X自身のページ読み込みを監視し、読み込まれた投稿メタデータからメディア情報を収集する。
3. メディアタイムラインの取得範囲が終了した場合、必要に応じて対象ユーザーの検索結果へ切り替えて古い投稿を継続探索する。

X内部仕様は変更される可能性があるため、取得部分は他のUI/ZIP処理から分離して修正しやすくする。

## 9. レジューム

作業そのものをレジューム可能にする。

### 9.1 収集フェーズ

収集中に次が発生しても進捗を保存する。

- 429 / アクセス制限
- ユーザーが「停止」を押した
- Chromeを閉じた
- PCを再起動した
- 通信切断
- 拡張機能の一時停止/クラッシュ

保存対象:

- 対象ユーザー
- 収集済みメディア一覧
- 最古/最後に確認したTweet ID
- 画像数 / 動画数
- 収集状態
- 最終更新時刻

同じユーザーを再度開いた場合のみ、前回作業を提示する。

```text
前回の作業があります
@ppp200x  収集済み 1,453件

[ 続きから再開 ] [ 最初から ]
```

別ユーザーを開いている場合は、他アカウントのレジューム通知を前面に出さない。

### 9.2 ZIP作成フェーズ

- 完成・保存済みZIPは確定済みとして扱う。
- 保存済みZIPへ後から追記しない。
- 中断後は次のZIP番号から継続する。
- 未完成のZIPは破棄し、そのチャンクのみ再作成する。

例:

```text
001.zip 完成・保存済み
↓
002.zip 作成途中で停止
↓
再開
↓
002.zip を作り直して続行
```

## 10. ポップアップUI

ポップアップサイズは固定。サムネイル一覧は表示しない。

「シンプル」シリーズの共通デザインを踏襲する。

主な色:

- 背景: `#e8e8e8`
- パネル: `#f7f7f7`
- 枠: `#d0d0d0`
- メイン青: `#4a8ce0`
- ホバー青: `#3a7bd5`
- ZIP保存緑: `#28a745`
- 緑ホバー: `#218838`

┌──────────────────────────┐

### 10.1 停止ボタン

「停止」はメディア収集用なので「メディアを収集」ボタンの横へ置く。

待機中はdisabled、収集中のみ有効化する。ボタン位置は固定し、状態変更によるUIのガタつきを避ける。

ZIP作成中の中止はZIP保存側の操作として別扱いにする。

### 10.2 ステータス領域

新しいメッセージ枠を多数増やさず、既存の進捗欄を「現在の作業状態を表示する共通ステータス領域」とする。

表示例:

通常:

```text
準備完了
メディアを収集してください
```

収集中:

```text
収集中…
投稿を確認中  1,453件検出
```

429:

```text
Xのアクセス制限により一時停止中
収集済み 1,453件 / 再開を待機しています
```

手動停止・再起動後:

```text
前回の作業があります
@ppp200x  収集済み 1,453件
[ 続きから再開 ] [ 最初から ]
```

収集完了:

```text
収集完了
画像 1,284件 / 動画 169件
```

ZIP作成:

```text
ZIPを作成中… 61%
media_002.zip  327 / 500ファイル
```

収集時は総件数が事前に確定しないため、誤解を避けるため進捗バーは原則インジケーター（不定進捗）として扱う。ZIP作成時は対象件数が確定しているため実進捗率を表示する。

### 10.3 ホバー表示

レジューム有無など重要情報をホバーだけに隠さない。

ホバーは詳細情報の補助に限定する。

例:

```text
開始: 2026/09/19 20:12
最終処理: 20:27
最後のTweet ID: ...
収集済み: 1,453件
```

## 11. Provider分離設計

SNS固有処理はProviderとして分離する。

想定構成:

```text
simple-marugoto-zip/
├─ providers/
│  ├─ x.js
│  ├─ bluesky.js
│  └─ threads.js
├─ core/
│  ├─ collector.js
│  ├─ downloader.js
│  ├─ archive.js
│  └─ resume.js
├─ popup/
└─ options/
```

Providerは共通形式のメディア情報を返す。

```text
platform
accountId / handle
postId
postedAt
mediaIndex
mediaType (image / video)
mediaUrl
extension
```

ZIP・分割・レジューム・進捗表示はProviderに依存しない共通処理とする。

---

## 12. 保存状態

`chrome.storage.local` を使用し、アカウント単位で収集状態を保存する。

想定キー:

```text
collections[@username]
```

収集データにはメディアURL、Tweet ID、メディア番号、種別、拡張子等を保持する。

ログインCookieそのものを拡張独自ファイルとして保存・書き出すことはしない。

## 13. 認証 / API設定

右上の歯車ボタンからオプション画面を開き、Providerごとの認証・API設定を管理する。

### X

`cookies.txt` をユーザーに書き出させる方式にはしない。Chromeで既にログインしているXのWebセッションを利用し、X自身のページが取得した情報を利用する方式を優先する。

### Bluesky

公開情報の取得は可能な限り認証不要の公式インターフェースを利用する設計とし、認証が必要な機能を追加する場合のみオプションを表示する。

### Threads

既存の `threads-token-tool` およびCross-post拡張で得たトークン運用の知見を再利用する。アクセストークン等が必要な場合はオプション画面で設定・更新できる構造とする。

### 保存方針

API関連値はソースコードへ固定埋め込みせず、ユーザー設定として管理する。秘密性の高い値は `chrome.storage.sync` でクラウド同期せず、原則 `chrome.storage.local` に保存し、入力欄はマスク表示する。

ユーザー操作の基本は:

```text
対象ユーザーを開く → 拡張を開く → メディアを収集 → ZIPで保存
```

とし、認証設定は必要なProviderでのみ初回・期限切れ時に行う。

## 14. 初期実装で対象外とするもの

- サムネイル一覧
- 個別メディア選択
- GIF専用フィルター
- 画像品質選択
- 画像フォーマット変換
- ファイル名カスタマイズ
- ソート順カスタマイズ
- 投稿日範囲指定
- いいね/ブックマーク等、プロフィール以外のコレクション取得
- Xの制限を迂回する仕組み

必要性が確認できた機能のみ後から追加する。

## 15. 注意事項 / README記載候補

> 本拡張は対応SNSから取得可能なメディア情報を利用して画像・動画を保存します。各SNS側の仕様変更により、一時的に動作しなくなる場合があります。

> 画像は常にXから取得可能な原寸解像度を優先して保存します。画像によってはファイルサイズが大きくなる場合があります。

> 動画にはSNS上のアニメーションGIF（MP4形式で配信されるもの）を含みます。

> 大量のメディアを収集する場合、X側のアクセス制限により一時停止することがあります。制限を検知した場合は無理に再試行せず、待機またはレジュームします。

> Xの仕様・利用規約は変更される場合があります。利用時点のルールを確認してください。

## 19. バージョン表記

本プロジェクトではKINAの既存ソフトと同じバージョン方針を使う。

- `v0.0.x` : テスト版・試作・不具合修正
- `v0.x.0` : 明確な機能追加を伴う開発版
- `v1.0.0` : 安定版 / 正式版の目安

各要素は整数として扱うため、`v0.0.9` の次は `v0.0.10` とする。

初回実装は **v0.0.1** から開始する。

## v0.0.2 テスト追加仕様

- 配布ZIP名にバージョンを含める。
- 配布ZIP内部の最上位フォルダ名は常に `simple-marugoto-zip` とする。
- ポップアップに「ダウンロードファイル数」を追加する。
  - `5ファイル（動作確認）`（テスト版の初期値）
  - `無制限`
- 5ファイルモードでは、1回のZIP保存処理で最大5ファイルの取得に成功した時点で安全に `archive_paused` へ移行する。
- 完成済みZIPには追記せず、次回の「ZIP保存を再開」で `nextItemIndex` と `nextZipNumber` から続行する。
- 例: `_001.zip` に1〜5件目を保存した場合、次回は6件目から `_002.zip` へ保存する。


## v0.0.3 接続安定化仕様

- 拡張の読み込み・更新前から開いていたXタブでcontent scriptが存在しない場合、background側からX用スクリプトを自動注入して再接続する。
- `main-hook.js` はMAIN world、`content.js` はISOLATED worldへ注入する。
- 二重注入時はガードで重複初期化を防止する。
- これにより通常のテストではXタブの手動再読み込みを必須としない。

## v0.0.19 追記: X手動スクロール収集

- ポップアップの対象ユーザー欄内に「自動／手動」の切り替えを配置し、選択を `smz_user_settings_v1` に保存する。既存利用者は自動が既定。
- 収集ジョブごとに `collectionMode` を持ち、429待機・再開・ページ再読み込み後もモードを維持する。ZIPは従来と共通。
- 手動時は拡張自身からスクロールを送信しない。`/media` をユーザーが読み込む過程でXのWeb版が取得したUserMedia等のレスポンスを利用する。
- 手動収集の完了はユーザーの明示操作のみ。通信処理／メディア追加処理が落ち着くまで完了せず、通信継続中は収集を維持したまま再操作を案内する。
- 初回ロードでcontent bridgeの起動より先に完了した応答は、MAIN hookで直近分を一時保管して橋渡し開始時に再送する。登録側のキー重複排除は必須。
- 自動収集の最終確認状態は `collectionPhase: final_check` でUIへ通知し、約30秒の待機理由を表示する。
- 手動モードでもXの利用許諾を保証するものではなく、公開前に規則・実機での取得精度を確認する。

## v0.0.21 追記: ZIPごとの状態ファイル／全体JSONバックアップ

- すべての新規分割ZIPに `ユーザー名/backup-state.json` を同梱する。分割ZIPごとの実際の保存確定位置、次のZIP番号、未保存メディア、種別の保存済み判定を保存する。差分収集中は退避済みの前回状態も保持する。
- 拡張全体のJSONは、すべてのアカウントの現在・退避状態と、画像／動画・分割数・収集モード等の共通設定を明示的な許可リストで書き出す。
- ZIP/JSONの復元は設定ページから行い、プレビュー・既存優先の追加・アカウント置換・全体置換の3方式を用意する。ZIP読取時は中央ディレクトリからJSON部分だけ取り出す。
- APIキー・アクセストークン・Cookie・パスワード、認証情報を含むURL、保存先フォルダ名・ハンドル・権限はバックアップに含めない。必要なCDN URLは許可されたドメイン・クエリパラメータのみ出力する。
- 以前のZIP本体の存在は検証できない。v0.0.20以前のZIPには状態ファイルがないため、旧版のデータ移行には全体JSONを利用する。
- `backup-state.json` はメディアの**実ファイル**の代わりにならない。状態を復元しても過去のZIP群そのものは別途保管する。

## v0.0.22 追記: 小サイズアイコン／復元の標準操作／全体初期化

- アイコンは青（通常）、緑（ZIP進行中・完了）の2状態。小サイズ16pxには専用の簡略図形を使用し、元絵の画像・動画＋下向き矢印＋ZIPの意味を保つ。Chromeバッジ（青、黄、緑、赤）と背景を競合させない。
