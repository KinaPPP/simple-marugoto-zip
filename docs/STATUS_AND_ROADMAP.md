## 1. プロジェクト概要

「シンプルまるごとZIP」は、SNSユーザーが投稿した画像・動画をまとめて収集し、ZIPとしてローカル保存するChrome拡張機能。

現在はXに対応。将来的にBluesky・ThreadsをProviderとして追加できる構成を前提とする。

### 名称

- 日本語名: **シンプルまるごとZIP**
- Repository / directory name: **simple-marugoto-zip**
- 配布ZIP例: `simple-marugoto-zip-v1.0.0.zip`
- 配布ZIP内部の最上位フォルダは常に `simple-marugoto-zip/` とし、フォルダ名にはバージョンを付けない。

### バージョン方針

- `v0.0.x`: テスト・試作版
- `v0.x.0`: 機能追加を伴う開発版の目安
- `v1.0.0`: 通常利用できる安定版の目安
- 各桁は整数として扱い、`v0.0.9` の次は `v0.0.10`

---

## 2. UI / UX 方針

シンプルシリーズ共通の思想として、**利用者に不要な操作を増やさず、主要操作を1画面で把握できるUIを優先する**。

### 現在のポップアップ

- 固定サイズ・原則スクロールなし
- 青: 収集などの主要操作
- 緑: ZIP保存
- 上から以下の順に配置
  1. ヘッダー / 設定
  2. 対象ユーザー
  3. メディア収集 / 停止
  4. 状態・進捗・レジューム
  5. 画像 / 動画件数
  6. 取得するメディア
  7. ZIP分割
  8. 動作確認用ダウンロード件数
  9. ZIP保存 / 中止
- 下端には、今後のフォント・文言変更による高さ増加を吸収するための余白を残す
- ステータス欄は固定高とし、状態メッセージ増加でポップアップ全体を伸ばさない

### メディア種別

UI上は以下の2種類のみ。

- 画像
- 動画（X上のアニメーションGIFを含む）

GIFはX上ではMP4として取得されるため、独立項目にしない。

### 画像品質 / 形式

- 品質選択UIは設けない
- Xから取得可能な**原寸解像度を常に優先**
- Xが配信しているJPEG / PNG等の形式をそのまま保存し、JPG / PNGへの統一変換は行わない
- README等に「原寸保存のため、画像によってはファイルサイズが大きくなる場合がある」と明記する

## 3. X Provider: v0.0.6 実装済み仕様

### 対象ユーザー判定

Xの以下のページ等からユーザー名を自動取得する。

- プロフィール
- `/media`
- 個別投稿

`/home` 等、対象ユーザーを一意に判定できないページは収集対象にしない。

### 収集方法

- Xの公式APIは使用しない
- X Webページが取得する `UserMedia` 系GraphQLレスポンスを監視してメディア情報を収集
- 必要に応じて対象ユーザーの `/media` へ移動
- 自動スクロールしながら古い投稿へ遡る
- 拡張読み込み前から開いているXタブでも、必要なcontent scriptが存在しない場合は自動注入して再接続

### 画像

- `pbs.twimg.com` の原寸版 `name=orig` を優先
- Xが配信している拡張子を維持

### 動画

- 通常動画: 利用可能なMP4 variantから最高ビットレートを優先
- animated GIF: MP4として保存し、UI上は「動画」に含める

### ファイル名

ZIP内部のメディアファイルは以下を基本とする。

`{Post/Tweet ID}_{投稿内メディア番号}.{拡張子}`

例:

```text
2101040138784829824_1.jpg
2101040138784829824_2.jpg
2101189548885831967_1.mp4
```

明示的なソートオプションは設けない。Tweet IDと投稿内番号で十分な規則性を持たせる。

## 4. ZIP仕様

### ZIP内部

画像と動画を別ZIPにはせず、**1系列のZIP内でフォルダ分け**する。

```text
ppp200x_20260919_230500_media_001.zip
└─ ppp200x/
   ├─ images/
   │  ├─ 2101040138784829824_1.jpg
   │  └─ 2101040138784829824_2.jpg
   └─ videos/
      └─ 2101189548885831967_1.mp4
```

### ZIPファイル名

`ユーザー名_YYYYMMDD_HHmmss_media/images/videos_連番.zip`

例:

```text
ppp200x_20260919_230500_media_001.zip
ppp200x_20260919_230500_media_002.zip
ppp200x_20260919_230500_media_003.zip
```

同じ保存作業をレジュームしている間は日時を固定し、連番のみ進める。

### ZIP分割

- 自動
- 500 MB
- 1 GB
- 500ファイル

自動は「300 MBまたは300ファイルの先に到達した条件」で分割。

完成済みZIPへの追記は行わない。再開時は次のZIP番号から保存する。

## 5. レジューム / 長時間バックアップ

### 収集状態

収集状態は `chrome.storage.local` に保存し、以下から復旧可能な設計とする。

- 手動停止
- Chrome終了 / 再起動
- 通信エラー
- X側アクセス制限

### 途中停止後の保存

収集完了前でも、手動停止時点までに取得できたメディアはZIP保存可能。

収集状態とZIP保存状態は別管理とし、途中でZIP保存した後でもXの収集を続きを再開できる。

### 5ファイル・動作確認モード

テスト用に以下を実装済み。

- `5ファイル（動作確認）`
- `無制限`

5ファイル指定時は、ZIPへ5件保存した時点で一時停止。
次回「ZIP保存を再開」で続きの6〜10件目、その次は11〜15件目という形で進む。

これは**収集上限ではなくZIP保存ファイル数の上限**。

---

## 6. X側制限への対応

- 429 / rate limitを検知した場合、強引な回避・高速再試行は行わない
- 待機または安全な停止を優先
- 長時間処理では「速さ」より「壊れない・抜けにくい」ことを優先する

XのWeb内部仕様変更で動作しなくなる可能性があるため、X固有処理はProviderへ分離して保守する。

## 9. 1000件以上の場合に警告

X表示件数が**1000件以上**の場合、収集開始前に以下のような確認を出す。

```text
このアカウントには約1,308件のメディアがあります。
収集に長時間かかる場合があります。

[ 収集を開始 ] [ キャンセル ]
```

大量件数でも収集そのものを禁止せず、利用者が判断できるようにする。

## 10. 自動スクロール / 収集の安定化

大量スクロール時にXのメディア一覧で白いサムネイルが生じることがある。
白表示は必ずしもメディア取得不能を意味せず、X側の遅延描画・仮想化・読み込み待ちの可能性がある。

v0.0.17では速度優先ではなく、以下のレスポンス待ちペーシングへ変更した。

```text
スクロール
  ↓
UserMedia等の関連通信開始を監視
  ↓
関連通信の終了 / レスポンス解析を待つ
  ↓
settle時間を置く
  ↓
次のスクロール
```

関連通信が発生しない場合だけ、約6.5秒以上空けて最下部を再確認する。固定1.8秒周期の盲目的なスクロールは廃止した。

目的:

- X UIの描画速度に依存しすぎない
- GraphQLレスポンスを取りこぼしにくくする
- 前の要求が処理中のまま次の読み込みを重ねにくくする
- 長時間バックアップ向けに安定性を上げる

## 12. 保存先の扱い（v0.0.15）

v0.0.15では、Chromeの「ダウンロード前に各ファイルの保存場所を確認する」がONでも分割ZIPごとにダイアログを繰り返さないよう、File System Access API対応環境では保存先フォルダを最初に1回だけ選択する方式を追加した。

```text
ZIP保存開始
  ↓
保存先フォルダを1回だけ選択
  ↓
001.zip
002.zip
003.zip ...
を同じフォルダへ連続保存
```

- `FileSystemDirectoryHandle` は拡張オリジンのIndexedDBへ保存する。
- 同じ収集作業のZIPレジュームでは同じ保存先を再利用する。
- 権限が失われた場合は安全に一時停止し、再開操作時にフォルダを再選択する。
- APIを利用できない場合は従来のChrome Downloads APIへフォールバックする。
- 保存先の絶対パス、Cookie、SNSパスワード等は保持しない。

## v0.0.7 実装済み: ポップアップ外の進捗可視化と誤操作防止

長時間バックアップでは保存ダイアログ等で拡張ポップアップが閉じるため、ツールバーアイコンを状態表示として利用する。

- 通常: 青アイコン
- 収集中: 青 + `収`
- 429待機: 青 + `待`
- ZIP保存中: 緑 + 1%単位の数字（0〜99）
- ZIP再開待ち: 青 + `続`
- ZIP保存完了（未確認）: 緑 + `✓` を保持。ポップアップを開くか次の処理を開始すると解除
- エラー: 青 + `!`
- ホバー時に処理件数・ユーザー名・進捗を表示

ZIP保存開始後はXタブに依存せずOffscreen Document側で処理を継続するため、他タブの操作や元のXタブからの移動を許容する。一方、ZIP保存中は収集系操作・設定変更をロックし、同一状態への競合操作を防止する。

## v0.0.15で実装: 保存先1回選択と連続ZIP保存

Chromeの「ダウンロード前に各ファイルの保存場所を確認する」がONの場合、分割ZIPごとに保存ダイアログが表示される。長時間バックアップでは負担が大きいため、File System Access APIを利用した以下の方式を検討・実装する。

```text
ZIP保存開始
  ↓
保存先フォルダを1回だけ選択
  ↓
001.zip
002.zip
003.zip ...
を同じフォルダへ連続保存
```

- 選択した `FileSystemDirectoryHandle` は拡張オリジンのIndexedDBへ保存可能
- 同じバックアップ作業中は分割ZIPごとの保存ダイアログを出さない
- 再開時に権限が有効なら同じ保存先を再利用し、必要な場合のみ再選択を求める
- API利用不可・権限取得失敗時は従来のChrome Downloads APIへフォールバックする

---

## バックアップ状態の保存と復元（v0.0.21）

各分割ZIPに `ユーザー名/backup-state.json` を同梱し、ZIP完成時点のチェックポイントを記録。最後のZIPからアカウント単位で復元できるが、過去のZIP実ファイルの存在までは検証しない。分割数が多い場合、状態ファイルの重複による容量増加に留意する。

設定タブから全体JSONエクスポート／インポートを行い、共通設定と全アカウントの現在・差分チェック用前回状態をまとめて移動できる。認証情報を含めない明示許可リスト方式を採用。保存先フォルダ権限は再選択が必要。

ZIP内状態ファイルと全体JSONはいずれも v0.0.21 の実装対象。別PCのChromeでの読み込み・レジュームは実機検証待ち。

## 増分バックアップ / 新着確認

一度全件収集が完了したアカウントで新しい投稿が増えた場合、毎回過去全件を再走査しない方式を検討する。

理想形:

```text
前回 newestPostId
  ↓
最新から新着を確認
  ↓
既知のPost IDへ到達
  ↓
新着分だけ追加・保存
```

収集中に一時停止した作業の「過去方向の続き」と、一度完了済みアカウントの「新着確認」は別の操作として扱う。

ZIP保存済み判定は配列位置ではなく、将来的には `{Post ID}_{mediaIndex}` のメディアキー単位で持つ方が、新着追加による並び順変化に強い。

## 18. 開発上の原則

1. ユーザーに不要な選択肢を増やさない。
2. 主要操作は可能な限りポップアップ1画面に収める。
3. 大量処理では速度よりレジューム可能性と安全性を優先する。
4. 完成済みZIPは再編集せず、新しいZIPへ続ける。
5. X側の制限は回避せず、安全に停止・待機する。
6. SNS固有ロジックはProviderへ閉じ込め、共通ZIP / UI / レジューム処理と分離する。
